## 三、小样本四路SVD实验

### 3.1 实验设计

从3000条全量数据中取90条（小样本），训练4种方法，各400步，对比Eff Rank。

**四种方法：**
- M0: Original teacher-student蒸馏
- M1: +VICReg正则化 λ=0.1
- M2: +VICReg正则化 λ=0.5
- M3: +I-JEPA自监督预训练

### 3.2 SVD分析脚本开发

**文件：** `experiments/analyze_checkpoints.py`

**8个评估指标：**
1. Effective Rank — 等价独立维数
2. RankMe — SSL表示质量
3. Top-5 Ratio — 前5维占比
4. CosSim Mean — Token间余弦相似度
5. Dead Dimensions — std<0.01的维度数
6. SmoothRankMe — 多尺度平滑熵
7. Spectral Gap — 奇异值最大比值
8. SV Gini — 奇异值分布均等度

### 3.3 遇到的bug及修复

#### Bug 1: Latent shape错误

**错误信息：** unpacking error from `generate_latent_batch`

**原因：** `generate_latent_batch`返回3D `[B, L, H]`而非预期的4D `[B, R, L, H]`。

**修复：** 在analyze_checkpoints.py中检测`lat.dim()`后处理：
```python
if lat.dim() == 3:
    lat_flat = lat.reshape(-1, H)  # [B*L, H]
elif lat.dim() == 4:
    lat_flat = lat.reshape(-1, H)  # [B*R*L, H]
```

#### Bug 2: ModelWrapper缺少args参数

**错误信息：** `AttributeError: '_DA' object has no attribute 'latent_space_realign'`

**原因：** ModelWrapper初始化时调用`self.args.latent_space_realign`，但analyze_checkpoints.py中创建的`_DA`类没有这个属性。

**修复：**
```python
class _DA:
    latent_space_realign = 0
```

### 3.4 小样本实验结果

| Checkpoint | Eff Rank | CosSim | Dead Dims |
|------|:---:|:---:|:---:|
| Original (M0) | **2.32** | 0.9990 | 4 |
| VICReg λ=0.1 | 1.89 | - | - |
| VICReg λ=0.5 | 5.42 | 0.9889 | 0 |
| I-JEPA (encoder) | **75.53** | 0.5378 | 0 |

**解读：**
- Original: 512维只用2.32维。CosSim=0.999表示所有token几乎完全相同。
- VICReg λ=0.1: 反而恶化(1.89)。正则太弱时引入噪声但不提供足够的防坍塌力。
- VICReg λ=0.5: 有改善(5.42)但远不够。需要>50才算健康。
- I-JEPA: Eff Rank 75.53是健康值。但注意：90条数据×400步=8.9 epoch。

**关键认知：** 此时误以为I-JEPA彻底解决了问题。后来发现这只是在大量epoch下的小数据结果。

## 四、全量数据六路实验

### 4.1 实验设计

使用`run_all_experiments.sh`一次性跑6个实验（EXP1-6），全量3000条数据。

**配置：** bs=2, steps=400, lr=2e-4, latent_steps=1024

### 4.2 遇到的bug

#### Bug 3: bs=16 OOM

**错误：** `torch.OutOfMemoryError: CUDA out of memory. Tried to allocate X GiB`

**分析：** 3090 24GB，Qwen3-VL-2B约占用15GB（模型+KV cache），bs=16时数据batch占用超限。

**测试过程：**
- bs=16: OOM（显存溢出）
- bs=8: 偶尔OOM
- bs=6: 安全(~15GB)
- bs=4: 安全(~11GB)
- bs=2: 最安全(~7GB)

**最终选择：** bs=2（安全优先）

#### Bug 4: Flash Attention 2对small models更慢

**测试结果：** FA2 39s/步 vs 普通attention 34s/步。FA2的kernel启动开销对小模型不划算。

**决定：** 不使用FA2。

#### Bug 5: 训练时间与epoch计算错误

**关键认知偏差：** 
- 小数据90条，bs=2，400步 = **8.9 epoch**
- 全量3000条，bs=2，400步 = **0.27 epoch**

之前的对比不公平——I-JEPA在小数据上"成功"是因为跑了8.9个epoch，每个样本被见了9次。全量数据只跑了0.27个epoch，模型连一轮数据都没看完。

### 4.3 全量实验结果

| Checkpoint | Eff Rank | CosSim | 训练时间 |
|------|:---:|:---:|:---:|
| original_full | 4.05 | 0.9755 | ~3.3h |
| vicreg05_full | 2.94 | 0.9972 | ~3.3h |
| ijepa_enc_full | 4.72 | 0.9864 | ~3.3h |
| ijepa_dec_full | 4.72 | 0.9864 | ~3.3h |

**关键发现：**
1. 所有方法在全量400步下Eff Rank都<5
2. I-JEPA encoder和decoder的Eff Rank完全一样(4.72)——encoder学到的表示在decoder训练中没有变化（因为freeze_encoder=1，但也说明decoder训练没改善encoder）
3. Checkpoint中没有`_steps`字段——训练脚本没保存训练步数，无法直接确认实际跑了多少步

### 4.4 磁盘空间问题

**问题：** overlay 30G用满至23G。

**清理过程：**
- 删除pip cache: 7GB
- 删除test checkpoints和旧logs
- 将`.partial.pt`×7(~1.1G)移到单独文件夹保留
- 清理后: 13GB空闲

**教训：** 30G磁盘对ML实验非常紧张。每个完整checkpoint约160MB，但训练日志、临时文件、huggingface缓存会快速填满。

## 五、分段训练管线

### 5.1 动机

想要看到Eff Rank随训练步数的变化趋势，证明两点：
1. 坍塌是渐进的还是突然的？
2. 更多步数是否会继续恶化？

### 5.2 方案设计

**配置：** bs=4, 750步, 每150步存checkpoint做SVD

**脚本：** `segmented_train.sh` + `svd_intermediate.sh`

### 5.3 遇到的bug

#### Bug 6: grep过滤吃掉了所有输出

**错误配置：**
```bash
2>&1 | grep -E "step=|loss=|Error|OOM" | tail -5
```

**问题：** grep的`tail -5`只保留最后5行匹配行，管道日志只剩1行。训练崩溃时看不到任何上下文。

**修复：** 不用grep过滤，完整保存日志：
```bash
> seg_pipeline.log 2>&1
```

或用`tee`同时输出到终端和文件：
```bash
2>&1 | tee seg_pipeline.log
```

#### Bug 7: OOM崩溃在step 340

```
step=340/750 loss=4.975 → CUDA OOM: tried alloc 3.84 GiB, only 2.61 GiB free
```

**原因：** 即使bs=4平均VRAM 11GB安全，某些step的VLM forward pass会有峰值分配。可能是长文本输入导致KV cache临时膨胀。

**结果：** 只有step 150和step 300两个中间checkpoint保留下来。

**分段实验结果：**

| Step | Eff Rank | CosSim | Dead |
|:---:|:---:|:---:|:---:|
| 150 | 3.61 | 0.9997 | 0 |
| 300 | 3.01 | 0.9993 | 2 |
| 340 | OOM崩溃 | - | - |

**解读：** Eff Rank从3.61降到3.01——训练越多坍塌越严重。CosSim维持0.999，Dead Dims增加到2。这证明坍塌不是随机初始化导致的，是训练过程系统性造成的。

#### Bug 8: GPU显存僵尸进程

**问题：** 训练进程被杀后显存不释放（21-23GB占用），`fuser -k /dev/nvidia0`无法清除。

**修复：** `kill -9`所有python进程，稍等几秒后显存自然释放。

#### Bug 9: SSH频繁断连

**问题：** 长时间运行的SSH连接会断开，导致后台任务失败。

**当前方案：** 使用`nohup ... &` + `disown`保持进程在SSH断开后继续运行。

**更好的做法（未实施）：** 用`tmux`或`screen`会话。

#### Bug 10: 训练日志丢失

**问题：** 多个实验的训练日志（`training_ijepa_full_encoder.log`, `training_original_full.log`等）不存在或被覆盖。

**原因：** 可能在清理磁盘空间时被删除，或`run_all_experiments.sh`的日志重定向有问题。

**唯一保留的日志：**
- `training.log` (197K, Jun 25) — 早期训练日志
- `seg_pipeline.log` (48K, Jun 28) — 分段训练的少量输出（grep过滤后）

## 六、三agent审稿与方案修正

### 6.1 审稿流程

启动了三个专业agent对研究方案进行严格审查：

| Agent | 专长 | 结论 |
|------|------|------|
| Agent 1 (路线A) | 梯度分析/训练动力学 | 梯度低秩可能是症状不是原因。需要时序分析+Hessian谱，不只是一阶梯度SVD |
| Agent 2 (路线C) | 密度估计/JEPA-SCORE | log\|det(J)\|计算不稳，OOD检测大概率花架子。50%概率变成纯分析段落 |
| Agent 3 (AC审稿人) | 综合评估 | 如果I-JEPA全量decoder Eff Rank<10，转纯诊断论文。下游无改善也转诊断 |

### 6.2 三agent共识

**致命问题（修改后方案必须解决的）：**

1. **没有下游任务评估** — 高Eff Rank ≠ 好的通信质量。随机噪声Eff Rank=512。必须有GSM8K/ARC-C/GPQA上M0 vs M3对比。
2. **因果claim过强** — "teacher-student导致坍塌"是相关性不是因果。降级为"我们发现坍塌伴随梯度方向集中化"。
3. **没有teacher侧分析** — 坍塌可能来自VLM原生表示而非UVC训练。必须先测teacher latent的Eff Rank。

**砍掉的内容：**
- OOD检测实验（另一篇论文的体量）
- 多agent安全性理论（另一篇论文的体量）
- log|det(J)|密度估计计算（不稳定且无额外信息）
- VICReg λ网格搜索（已有λ=0.1/0.5足够说明问题）

**保留的核心：**
- C1（40%）：发现并量化维度坍塌 + 证明teacher侧正常
- C2（35%）：梯度SVD + Hessian谱 + CKA揭示机制
- C3（25%）：I-JEPA修复 + 下游验证 + Jacobian谱诊断工具

### 6.3 Go/No-Go决策标准

| 条件 | 决策 |
|------|------|
| I-JEPA全量Eff Rank>30 + GSM8K M3≥M0 | **GO** 冲ICLR |
| Eff Rank 10-30 + GSM8K持平 | **YELLOW** 继续但降低预期 |
| Eff Rank<10 或 下游M3更差 | **NO-GO** 转纯诊断论文 |

### 6.4 投稿目标

- **ICLR 2027**（约10月截止）：representation learning核心赛道
- 备选：NeurIPS 2027（约5月截止），ICML 2027（约1月截止）

## 七、I-JEPA重训验证

### 7.1 为什么需要重训

Day 1 SVD分析揭示全量I-JEPA的Eff Rank只有4.72，远低于小数据的75.53。三agent讨论后认为是训练不充分：0.27 epoch vs 8.9 epoch。

### 7.2 代码修改

`train_ijepa_fixed.py`原来没有checkpoint_every功能。添加：

1. `--vision_codec_checkpoint_every` CLI参数
2. opt.step()后的中间checkpoint保存逻辑
3. 最终checkpoint保存`_steps`字段

**注意：** 之前所有checkpoint都没有`_steps`字段，无法从checkpoint反向推断训练了多少步。

### 7.3 第一次尝试（bs=2，后来取消）

- 配置: bs=2, 2000步, checkpoint_every=200
- 问题: bs=2每epoch需要1500步，2000步只有1.33 epoch。2 epoch需要3000步（~27h）。
- 状态: 启动了但很快被取消

### 7.4 第二次尝试（bs=3，进行中）

**配置：**
```
bs=3
steps=2000 (2 epoch, 每epoch=1000步)
lr=2e-4
checkpoint_every=200
output: checkpoints/codec_qwen3_ijepa_full_data_enc_v2.pt
log: ijepa_v2.log
```

**启动时间：** Jun 28 11:35

**VRAM使用：** ~7GB (安全，上限24GB)

**每步耗时：** ~32.5秒

**时间估算：**
- step 200: ~1.8h
- step 400: ~3.6h
- step 600: ~5.4h
- step 1000 (1 epoch): ~9h
- step 2000 (2 epoch): ~18h

### 7.5 中间SVD结果

| Step | Epoch | Eff Rank | RankMe | CosSim | Dead | 分析时间 |
|:---:|:---:|:---:|:---:|:---:|:---:|------|
| 200 | 0.2 | 2.31 | 1.02 | 0.9994 | 0 | Jun 28 ~13:30 |
| 400 | 0.4 | 7.54 | 1.14 | 0.9836 | 0 | Jun 28 ~15:30 |
| 600 | 0.6 | **14.29** | 1.20 | 0.9773 | 0 | Jun 28 ~17:30 |

**趋势分析：**
- Eff Rank单调上升：2.31 → 7.54 → 14.29
- CosSim持续下降：0.9994 → 0.9836 → 0.9773（token间终于有差异了）
- 每0.2 epoch，Eff Rank约翻倍
- 按当前趋势，step 1000-1200（1-1.2 epoch）应超过50

**关键验证：** 这证实了之前的假设——全量I-JEPA Eff Rank=4.72纯粹是欠训练(0.27 epoch)，不是方法在全量数据上失效。

### 7.6 Loss变化

```
step  40: loss=0.3344  pred=0.2457  var=0.8548  cov=0.0320
step  70: loss=0.1268  pred=0.0387  var=0.8458  cov=0.0358
step 160: loss=0.0877  pred=0.0002  var=0.8313  cov=0.0437
```

Prediction loss快速下降（0.25→0.0002），说明predictor已经完美学会了预测target。AC loss稳定（var~0.85, cov~0.04），方差约束有效。
